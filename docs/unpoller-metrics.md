# UniFi polling and its Prometheus metric inventory

## Outcome

`platform/unpoller/` deploys unpoller 2.34.0 as a single-replica Deployment in
the `monitoring` namespace. It polls the UniFi controller at
`https://192.168.10.1` with an API key from OpenBao and exposes Prometheus
metrics only. Prometheus scrapes it through a ServiceMonitor. The InfluxDB
output is disabled, so no second time-series sink exists.

The Argo CD Application is `clusters/kepler/apps/unpoller.yaml`, registered in
`clusters/kepler/apps/kustomization.yaml` next to the other platform apps. It
uses project `platform`, sync wave 6, and `CreateNamespace=true`.

## Configuration

| Setting | Value | Reason |
| --- | --- | --- |
| `UP_UNIFI_DEFAULT_URL` | `https://192.168.10.1` | Controller address. No gateway setting is changed. |
| `UP_UNIFI_DEFAULT_API_KEY` | `secretKeyRef: unpoller/api_key` | Value never appears in git. |
| `UP_UNIFI_DEFAULT_VERIFY_SSL` | `false` | Controller certificate is self-signed. |
| `UP_UNIFI_DEFAULT_SAVE_SITES` | `true` | `unifi_site_*` metrics need site data. |
| `UP_INFLUXDB_DISABLE` | `true` | Prometheus is the only output. |
| `UP_PROMETHEUS_NAMESPACE` | `unifi` | Metric prefix. Default would be `unpoller`. |
| `UP_PROMETHEUS_HTTP_LISTEN` | `0.0.0.0:9130` | Service and ServiceMonitor port. |

The image is
`harbor.homelab.pastelariadev.com/ghcr/unpoller/unpoller:v2.34.0@sha256:73423ddfe304e866b2cda2d3ecf8e68c15317c93a22945ad7d941d3ca3a6d022`.
Upstream publishes unpoller on GHCR, not Docker Hub, so the `ghcr` Harbor
project carries it, matching the other ghcr-sourced platform apps.

## Secret path

`ExternalSecret unpoller` copies one field: `platform/unifi` → `api_key`, into
Secret `unpoller` key `api_key`. It uses ClusterSecretStore `vault-platform`,
whose namespace condition already includes `monitoring`.

The platform ESO AppRole needs no change. Its policy is generated by
`vault_policy.gitops_lane` in `homelab-iac`
(`components/openbao/modules/runtime-secret-foundation/main.tf`), where the
`platform` lane grants:

```hcl
path "secret/data/platform/*" {
  capabilities = ["read"]
}
path "secret/metadata/platform/*" {
  capabilities = ["read", "list"]
}
```

`secret/data/platform/unifi` matches `platform/*`. No OpenBao query or policy
change was made.

## Scrape path

`platform/monitoring/values.yaml` leaves `serviceMonitorSelector` unset, and
kube-prometheus-stack 92.22.0 sets `serviceMonitorSelectorNilUsesHelmValues:
true`. Prometheus therefore selects ServiceMonitors labelled
`release: monitoring` in the release namespace. The ServiceMonitor here has
that label and sits in `monitoring`, matching the existing `blackbox-exporter`
ServiceMonitor. The repository already allows `ServiceMonitor` in the
`platform` AppProject.

## Verification

- `kubectl kustomize platform/unpoller` renders Service, Deployment,
  ExternalSecret, ServiceMonitor, and NetworkPolicy. kubeconform accepts the
  output with `-strict -ignore-missing-schemas`.
- `tests/unpoller-contract.sh` asserts the secret reference, absence of a
  secret literal, digest pin, NetworkPolicy scope, scrape path, and app
  registration. `scripts/validate.sh` runs it.
- Local run of `ghcr.io/unpoller/unpoller:v2.34.0` with the same env logged
  `Using NEW UniFi controller API paths given an API Key was provided`,
  `Prometheus is enabled`, `Prometheus exported at http://0.0.0.0:9130/ -
  namespace: unifi`, and no enabled InfluxDB output. `/health` returned 200.
- The controller answered the poll (`401` for a dummy key), so egress and TLS
  bypass reach the gateway. The real key was not read.

## Limits and remaining work

- The Harbor mirror path is the same shape as other ghcr platform apps. If the
  `ghcr` Harbor project is proxy-cache rather than pre-mirrored, the first pull
  populates it; the digest pin still verifies the content.
- Grafana dashboards are a separate slice. Use the names above as written.
- `unifi_client_*` and `unifi_site_*` counts depend on what the controller
  returns. Missing families are absent series, not zero values.
- The pod runs as the image's default user (root). It drops all capabilities,
  disables privilege escalation, and uses a read-only root filesystem.

## Key rotation and certificate renewal

Rotating `secret/platform/unifi` updates the Kubernetes Secret, but a running
pod keeps the environment value it started with. Order matters:

1. Wait for External Secrets to copy the new value into `Secret/unpoller`:
   `kubectl -n monitoring get secret unpoller -o jsonpath='{.metadata.resourceVersion}'`
   must change. Do not print `.data`; that is the base64 key. Otherwise the
   replacement pod loads the old key again.
2. Restart and wait: `kubectl -n monitoring rollout restart deployment/unpoller`
   then `kubectl -n monitoring rollout status deployment/unpoller`.
3. Confirm fresh controller metrics before revoking the old key. The
   NetworkPolicy admits only the Prometheus scraper, so query Prometheus
   rather than the pod:
   `curl -fsS 'https://prometheus.homelab.pastelariadev.com/api/v1/query?query=unifi_device_uptime_seconds'`
   must return a current sample for the gateway.

Rollout status alone does not prove the controller accepted the new key.

`platform/unpoller/ca-configmap.yaml` carries the controller's self-signed
certificate (CN=unifi.local, expires 2028-11-12). Replace it when the
controller certificate changes, then roll the Deployment in the same change:
the mounted PEM updates in place, but Go caches the root pool after first use,
so a running exporter keeps rejecting the renewed certificate until it
restarts. Verify with the same metrics check.

The exporter reaches the gateway through a hostAlias on that name because the
certificate has no SAN for 192.168.10.1.
